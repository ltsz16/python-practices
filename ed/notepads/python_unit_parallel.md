# Python Parallel Testing

## Introduction

In order to maintain high confidence in code quality, an application needs to have quality tests and those tests must reach a desirable coverage target. The more automated tests are executed during build time, the longer the build takes to complete. Longer builds lead to longer feedback loops to verify if the code pushed to the repository works as intended.

One way to decrease build time is by having the tests run in parallel. During research into parallel testing approaches, the following benefits were detected when run against unit and integration tests:

- **Roughly 50% faster test execution**

## Parallel Test Frameworks

The following frameworks were studied for parallel testing capabilities:

### Nose

Nose has a big limitation that makes it not the appropriate option for many use cases. Since coverage reports are often needed to check if coverage targets have been reached, Nose's inability to run tests in parallel and calculate test coverage simultaneously is a significant drawback. (See [plugin interaction warning](https://nose.readthedocs.io/en/latest/)).

Additionally, Nose requires markers to be added to tests, which imply code changes in order to run the tests in parallel.

### Pytest

**Pytest is the recommended option** for parallel testing. Pytest provides all core features that Nose provides plus integration with a coverage plugin. This makes it the best option for use cases requiring coverage reports.

Similarly to Nose, pytest can run any test case that extends the `unittest.TestCase` class.

## Pytest Installation

In order to install pytest, run the following commands:

```bash
pip install pytest
pip install pytest-parallel
pip install pytest-cov
```

## Running Pytest In Parallel

The example below shows how to run pytest in parallel with 4 workers. It is wise to set the number of workers equal to the number of CPU cores:

```bash
pytest --workers 4 -v --junitxml="unit-test-reports.xml" --cov=apscloudtools --cov-report html:coverage_html_report integration_tests/
```

### Command Options Explained

- `--workers 4` — Run tests with 4 parallel workers (set equal to number of CPU cores)
- `-v` — Verbose output
- `--junitxml="unit-test-reports.xml"` — Generate a test report named "unit-test-reports.xml"
- `--cov=apscloudtools` — Points to the directory that contains source files to measure coverage
- `--cov-report html:coverage_html_report` — Generate an HTML report in the directory "coverage_html_report"
- `integration_tests/` — The directory that contains the integration tests

## Challenges: Making Tests Concurrency Safe

Tests run in parallel must be **concurrency safe**. In other words, they must not depend on mutable shared resources. Examples of problematic resource sharing include:

- Writing/deleting the exact same file
- Changing shared static variables
- Modifying shared database records
- Accessing shared temporary directories

It's up to the team that chooses the parallel testing approach to assess the effort necessary to make their tests concurrency safe.

### Best Practice

**Unit tests, if implemented correctly, should be able to run in parallel without any changes.**

When writing unit tests, follow these principles:

- Use unique temporary files or directories for each test
- Mock or isolate external dependencies
- Avoid modifying global state or static variables
- Use fixtures or setup/teardown methods to ensure isolation
- Use in-memory databases or test databases isolated per test

## Jenkins Integration: JUnit Plugin

Thanks to the Jenkins JUnit plugin, integration of pytest test reports and coverage results into the Jenkins UI is straightforward.

The example below shows a Jenkins JUnit plugin configured to read the "unit-test-reports.xml" test report and the coverage report found in "coverage_html_report".

### Jenkins Pipeline Configuration

```groovy
post {
    always {
        junit testResults: 'unit-test-reports.xml'
        publishHTML(target: [
            allowMissing: false,
            alwaysLinkToLastBuild: true,
            keepAll: true,
            reportDir: 'coverage_html_report',
            reportFiles: 'index.html',
            reportName: 'Coverage Report',
            reportTitles: 'Coverage Report'
        ])
    }
}
```

### Configuration Breakdown

- `junit testResults: 'unit-test-reports.xml'` — Reads the JUnit XML test report generated by pytest
- `publishHTML(target: [...])` — Publishes the coverage HTML report to Jenkins
  - `allowMissing: false` — Fail the build if the report is missing
  - `alwaysLinkToLastBuild: true` — Always link to the latest build's report
  - `keepAll: true` — Keep all historical reports
  - `reportDir: 'coverage_html_report'` — Directory containing the coverage report
  - `reportFiles: 'index.html'` — The main HTML file to display
  - `reportName: 'Coverage Report'` — Name shown in Jenkins UI
  - `reportTitles: 'Coverage Report'` — Title displayed for the report

## Summary

Parallel testing with pytest offers significant performance improvements (~50% faster execution) while maintaining comprehensive test coverage reporting. The key to success is ensuring tests are properly isolated and don't share mutable resources. When implemented correctly, parallel testing can dramatically reduce build times and provide faster feedback on code quality without additional code modifications to the tests themselves.
